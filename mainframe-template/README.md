# MainFrame Templates

Starting a project from a template, filled in through MainFrame's own data entry framework.

> **Using it from MainFrame?** [docs/using-templates.md](docs/using-templates.md) is the guide — the form, the
> folder chooser, what each refusal means, and how to keep your answers for next time. This file is about how
> the thing is built and how to write a template of your own.

```
~ > templates
id             title                         summary                                          files
vexel-desktop  VexelRay desktop application  a window on vexelray-gui, wired the way the ~     15

~ > new vexel-desktop
```

That second line puts up a form — the whole screen at once on a display, printed downwards on a terminal —
asks where the project goes with a folder chooser, checks every answer, and then says what it is about to do
before it does any of it.

```
~ > new vexel-desktop --dry-run
dry run create 16 items -- nothing was changed
  would make plotter
  would write plotter/pom.xml
  would write plotter/src/main/java/dev/acme/plotter/Plotter.java
  ...
  then: cd plotter && mvn compile exec:exec
```

## The three ways to answer

The same rules hold all three, which is the point of a form being data: the check that stops a typo at the
keyboard is the check that stops it in a record a script built.

```
new vexel-desktop                                                   # the form
new vexel-desktop --in=~/src --set={artifactId: "plotter"} --no-ask # a line
echo {artifactId: "plotter", where: ~/src} | new vexel-desktop --no-ask
form-recall my-defaults | new vexel-desktop                         # answers you kept last time
```

`templates <id>` prints exactly what a template will ask for, as rows, so a script can be written against it
rather than against this README.

## What it refuses, and why

Everything is worked out before a byte is written — the answers, the destination, every file's contents, and
the list of files against what is on disk. A template that would fail on its last file fails before its first,
which for a project is the difference between no project and half a project. If a write does fail part way, the
step that failed takes back what the earlier ones made.

| | |
| --- | --- |
| an answer that would not compile | a package part that is a Java keyword, a class name starting with a digit, an artifactId Maven will not take |
| a folder that already has things in it | unless `--into`, which allows the folder and nothing else |
| **a file that is already there** | **always, with no flag** — see below |
| XML that will not parse | checked over the generated bytes, so a stray `<` in an answer is caught too |
| a library that is not installed | said out loud rather than refused: the local Maven repository is checked for everything the template declares it `needs` |

**The one rule with no flag.** A file that is already on disk is never written over. `--into` allows the folder
to exist and to have things in it, because putting a project into a folder somebody already made is an ordinary
thing to want; it does not allow one single existing file to be replaced. Everything else this command can get
wrong is undone by deleting the folder. That one is not.

## Writing a template

A folder in `~/.mainframe/templates/<id>/` with a `template.manifest` and a `files/` beside it. The same two
things a bundled template has, read by the same reader, so writing one is copying one out and editing it — and
one of yours with the same name as a bundled one wins.

```
template  vexel-desktop
title     VexelRay desktop application
folder    ${artifactId}
next      cd ${artifactId} && mvn compile exec:exec

slot artifactId
    label     project name
    required  yes
    preset    my-app
    match     [a-z][a-z0-9]*(-[a-z0-9]+)*
    rule      maven-id

fill blank  packageName  package  ${groupId}.${artifactId}
fill always packagePath  path     ${packageName}

file pom.xml
file src/main/java/${packagePath}/${className}.java  from App.java
file src/test/java/${packagePath}/ModelTest.java     from ModelTest.java  when tests

needs dev.vexelray.gui:vexelray-gui-widget:${guiVersion}
```

A `slot` is asked for. A `fill` is worked out — `always` for a value nobody should be asked about, `blank` for a
slot somebody was offered and left empty, which is how "leave it blank for the obvious thing" is a real offer.
`next` is what to tell somebody once it is written, and it comes from the template because only the template
knows: a Maven project ends with `mvn compile exec:exec` and a folder of notes ends with nothing at all.
A `slot` with `choose` becomes a dropdown on a panel and a numbered list on a terminal.
Substitution is `${name}` and nothing else: no expressions, no conditionals, no loops. `$${name}` is a literal
`${name}`, which is what lets a generated pom keep Maven's own properties.

**Every file a template writes is listed.** Not tidiness: a bundled template's files are classpath resources,
and a classpath directory cannot be enumerated in a native image, so the `file` lines are the only record of
what is in it. `VexelDesktopTest.theManifestAndTheFolderAgree` holds the list and the folder together, because
the failure otherwise is a file that quietly stops shipping.

## What is in the box

`vexel-desktop` follows [`calculator-vexel-demo`](https://github.com/sibarum/calculator-vexel-demo), the
reference implementation of the VexelRay stack. What is copied is its *shape* rather than its content -- the
wiring, the threading model, the build, and the two documents a project of this kind keeps. What a
new project draws is a heading and a counter, deliberately: every seam is wired and none of them is pretending
to be somebody else's application.

| | |
| --- | --- |
| `<Main>Wiring.java` | what the application builds, one method per `vexelray-framework` phase: the look, the model, the tree, the driving socket |
| `<Main>.java` | the entry point and the constants. The application edge -- input backend, clipboard, window memory, the clock, the frame loop and its wakes -- is the framework's, and used to be three hundred lines here |
| `Model.java` / `Doc.java` | one authoritative state, changed by relative edits committed through atchung's `State` |
| `Ui.java` | the tree, holding no state; `show(Doc)` writes everything derived from the document |
| `Look.java` / `Type.java` / `Landmarks.java` | the three vocabularies: colour, size, and the names an automation script may depend on |
| `Capture.java` | a headless PNG, with the note about what a capture cannot show |
| `docs/framework-notes.md` | seeded with how to write a finding, and one finding to start from |

## Layout

Two packages, and the line between them is the module's whole reason for being one.

- `dev.mainframe.template` — the engine. Reads a template, works out what files it would write, refuses the
  ones it should not. Imports nothing from MainFrame and nothing from anywhere else: `Scaffold` and `Checks`
  would drop into an installer or a Maven mojo unchanged.
- `dev.mainframe.template.shell` — the adapter. Slots become MainFrame form fields, answers become a record,
  the result becomes a `Plan`. Not meant to be reusable, which is why it is a package of its own.

The price of that line is small duplication — the engine parses its own manifest and measures its own edit
distance rather than borrowing the shell's. That price is the proof the boundary is real.

## Installing it

```java
Registry registry = Registry.standard();
Templates.install(registry);
```

`mainframe-dist` does this, so `mainframe.exe` carries the template as resources and can start a VexelRay
project on a machine with nothing but a JDK and a Maven repository. The resource globs a native image needs are
in this module's own `reachability-metadata.json` — without them the image builds clean, lists the template,
asks every question and then cannot find a file to write.
